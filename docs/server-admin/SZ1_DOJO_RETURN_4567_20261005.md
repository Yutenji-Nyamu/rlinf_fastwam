## 为什么反复，修到了哪里

- **目前能恢复运行，尚未定位最初的触发条件。** CUDA700是GPU非法内存访问，错误发生后进程的CUDA状态可能持续不可用；Vulkan DEVICE_LOST则是图形设备执行失效。日志能确认失败层次，但没有给出首个出错kernel／场景对象，因此不能把同类现象全部认作同一根因。[CUDA官方说明](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__TYPES.html)
- **重启／复位修复的是故障后的状态。** 本次7卡重启应用仍在初始化失败，单卡复位后原配置能继续，证明复位对本次恢复有效；触发条件没有改变，所以仍可能复发。NVIDIA对Xid109给出的立即处置是RESET_GPU、进一步处置是CONTACT_SUPPORT，并不表示已修复根因；本次5卡Xid13/43也不能直接等同于此前109。[NVIDIA Xid目录](https://docs.nvidia.com/deploy/xid-errors/analyzing-xid-catalog.html)
- **存在明确兼容性风险，但还不是根因证据。** 当前为H100、驱动575.57.08、Isaac Sim 5.1链路；官方明确不支持无RT Core的A100/H100。这使GPU物理／渲染／驱动组合值得重点排查，不能据此直接判定硬件损坏、显存不足或N25是原因。[Isaac Sim 5.1要求](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/requirements.html)
- **管理层问题与GPU崩溃分开记录。** 本次已修owner使用的Python缺少pidfd接口；临时proc权限导致的清理中断已定点收尾，未声称其权限变动根因已解决。这些修复负责可靠退出和RLT接替，不能修复PhysX／Vulkan内部错误。

要进一步找根因，需要固定失败任务与种子，取得首次GPU故障的最小复现／崩溃转储，再在受支持RTX设备或经确认的驱动组合上做单因素对照。该对照尚未执行；本轮只发布恢复记录，不改动运行实验或升级共享机器驱动。
