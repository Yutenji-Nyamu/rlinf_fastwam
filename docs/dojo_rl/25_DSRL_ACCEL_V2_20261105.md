## 每项依据、机制和结论

| 候选 | 怎么省时间 | 本次结论 |
|---|---|---|
| CPU 上检查 U 权重 | 权重原在 CPU，先检查再搬运，省 GPU→CPU 的布尔判断等待 | 两 bench 数值检查过，但没有稳定额外收益，关闭 |
| Torch 2/4 线程 | 小网络减少线程管理开销，或增加 CPU 并行 | 两 bench 无稳定收益；RT2 4线程另有一次策略输出略超阈值，关闭 |
| NUMA 绑核 | 让进程靠近该 GPU 所在 CPU 插槽，减少跨插槽访问 | SAC 无稳定收益；RT2 环境交互几乎不变，关闭 |
| actor 更新时不算 Q 参数梯度 | 保留动作导数，省当前不使用的 Q 参数反传 | 单次数学对照过，但完整 FSDP 生命周期失败；核心实现已撤回，没有有效速度结论 |
| Dojo 控制状态复用＋取消渲染限速 | 只复制需要的关节状态；同次控制共用展开结果；保持帧数，只去掉真实时间等待 | 候选和原配置重复均未过动作阈值，无法归因，全部关闭 |
| 上项＋4物理线程 | 调线程数，保持物理步长和求解器不变 | 同上，关闭 |
| 关闭无用 viewport | 减少无界面运行时的 UI 更新 | 现场本来已关闭，不重复计益 |

来源逐项锁定在 [sources.json](../../tools/dsrl_accel_v2/sources.json)：CPU/U/NUMA 依据 [PyTorch 性能指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)；Q 梯度思路依据 [Spinning Up SAC 固定版本](https://github.com/openai/spinningup/blob/038665d62d569055401d91856abb287263096178/spinup/algos/pytorch/sac/sac.py)；Dojo 三项来自 [RoboScope-Kit `30158a77` 的实验补丁](https://github.com/MINT-SJTU/RoboScope-Kit/tree/30158a77ae222701f5c31c327ebdc5085281b6fa/benchmarks/robodojo/patches)；viewport 依据 [Isaac Sim 性能指南](https://docs.isaacsim.omniverse.nvidia.com/latest/reference_material/sim_performance_optimization_handbook.html)。RoboScope 自身也将这些 Dojo 候选默认关闭。

底层直接用现有 PyTorch/Isaac API，借鉴外部实现并适配到当前数据流；没有替换 RLinf 的训练循环、回放语义或 Q 聚合。原生 RoboDojo 安装不改，适配限定在测试/正式进程内，并核对原生 RobotManager 源码哈希。

## SAC 实测

基线包含各 bench 已采用组合。每种方案正序/逆序各测一次，每次恢复同一完整训练状态和随机状态，5次预热＋100次更新计时；5个20次更新窗口取中位数。B256，真实续训点 replay：Dojo 758 条、RT2 3,246 条，路径见[实际输入回执](evidence/accel-v2-20261105/live-receipt.json)。下表单位 ms/update，不能当 π0.5 推理或整轮倍率。

| 配置 | RT2 正序 / 逆序 | Dojo 正序 / 逆序 |
|---|---:|---:|
| 现有基线 | 101.77 / **91.04** | 98.64 / **89.68** |
| CPU U 检查 | 105.44 / 91.49 | 100.67 / 89.26 |
| CPU U＋2线程 | 104.65 / 92.57 | 103.06 / 104.47 |
| CPU U＋4线程 | 90.86 / 105.02 | 102.34 / 103.08 |
| CPU U＋NUMA | 92.17 / 91.53 | 103.82 / 103.42 |

两次基线自己就相差约10%～12%，因此不能只挑一个最快点。采用门槛预先设为：相对两次中更快的基线，合并计时至少1.05×，两个重复各至少1.03×，并通过数值检查；最终都选择 baseline。原始结果：[RT2 SAC](evidence/accel-v2-20261105/rt2-sac.json)、[Dojo SAC](evidence/accel-v2-20261105/dojo-sac.json)。

每组恢复在线/目标参数、shadow、Adam/alpha、调度器和随机状态；更新后比较在线参数、优化器张量、抽样随机状态及固定观测/同噪声策略输出。参数容差为 `max(1e-3, 2×基线重复偏差)`，策略噪声 RMSE<0.002、最大差<0.02。RT2 4线程正序 RMSE=0.00201449，未放宽门槛。其它候选通过短测只说明在该容差内，不能声称长程训练或轨迹逐位相同；当前检查也没有单独输出更新后的目标参数/shadow偏差，下一次拟采用候选时应补齐。

## 环境实测

8环境，各执行100个控制动作：RT2 5×20，Dojo 2×50；正式最大长度仍200/700。每个候选回放基线动作，核对请求/实际布局、状态、奖励和终止，再以当前图像和相同噪声计算模型动作与 U，包括最后一次观测。状态最大差≤1e-4，动作 RMSE≤0.002/最大差≤0.02，U最大差≤0.001，奖励及 done/trunc 严格一致。

| RT2 配置 | 交互秒 正序 / 逆序 | reset＋交互秒 正序 / 逆序 | 对照 |
|---|---:|---:|---|
| 原配置 | 23.70 / 23.76 | 78.97 / 78.88 | 全过 |
| 2线程 | 24.52 / 23.92 | 78.13 / 80.11 | 全过 |
| NUMA | 23.56 / 23.79 | 74.31 / 76.65 | 全过 |

RT2 六组的状态、图像、模型动作、U 误差均为0，但交互没有足够收益；NUMA 的总时长改善也未达到两次都稳定获益的要求。六组结果与 baseline 选择已完整落盘，随后测试进程退出阶段 SIGSEGV（-11）。这不是干净的进程验收通过；phase guard 再次恢复原配置，正式训练使用新进程。[RT2 环境原始记录](evidence/accel-v2-20261105/rt2-env.json)

Dojo 原配置交互74.18秒，reset88.55秒。候选动作 RMSE：控制复用＋取消限速0.00585/0.00581，叠加4物理线程0.01292/0.00444；原配置重复也达0.00465，超过0.002。**因此当前对照不能证明候选改变了数据，也不能证明它等价或可采用。** 不提高阈值强行通过，所有新 native 开关恢复 `{}`。当时失败分支只落下异常，未保留其完整计时，不能补造速度表；后续测试入口已改为先保存误差/计时再作判定。[Dojo 环境记录](evidence/accel-v2-20261105/dojo-env.json)

现场诊断：Dojo CPU physics、8物理线程、manual timestep=render timestep=0.04，rate limiter开启，viewport存在但更新已关闭。没有跳过相机渲染、移除当前帧同步、减少去噪步数或训练更新。

## 接入失败也保留记录

- Dojo 第一次诊断发生在 lazy simulator 创建前，已移到原生 reset 后；RLT在重试准备期承接。
- Q detach 单次 Q/动作导数一致，但之后 FSDP 参数 allowlist 缺少 q_head；两份模型核心源码恢复为上一版，失败补丁只放 `rejected/`，安装器不应用。后续案例在已损坏 FSDP 状态中的结果无效。
- RT2 首轮更换线程触发 torch.compile 重编译次数限制，后续结果无效。重试在每个方案预热前清理进程内编译缓存，计时不包含这一步；正式训练不每次清缓存。[PyTorch 2.11 reset](https://docs.pytorch.org/docs/2.11/generated/torch.compiler.reset.html)
- 独立环境测试入口补齐正式 EnvOutput 已提供的 `extra_view_images=None`，修正 CUDA 可见设备；RT2 正常 reset 复用一个包装器，避免把 gym.close 的空实现当销毁保障。
- GPU7 重试在登记新 owner 后遇到 FQL 汇合日志重名，此时旧 owner 仍训练。只补完既已登记的交接，日志名加入部署名和PID，FQL等待对象更新成功。

失败尝试与最终配置均在现场回执中。完整短测失败自动关闭该阶段的新开关后继续正式训练；外层 owner 故障由既有 RLT 接手。准备期保持旧正式任务或 RLT 运行；切换只针对登记的 UID/PID/start，不动 GPU0–3 和其他用户。

## 从时间结构决定下一轮

测试前本次现场采集的[计时快照](evidence/accel-v2-20261105/timers-before.json)，不是早前15:22的旧日志：

| +U 任务 | 训练更新 | 采样/环境 | 下一层 |
|---|---:|---:|---|
| RT2，最近5个已学习轮中位数 | 141.7秒 | 108.5秒 | 环境 bootstrap/reset约57.0秒，交互44.8秒；策略predict约4.24秒 |
| Dojo，快照中最新已学习轮 | 177.6秒 | 593.9秒 | 临近完整native wave：reset52.6秒、动作执行282.4秒、观测257.5秒 |

这些计时层级有包含/并行关系，不能把所有列再相加。Dojo 最近5轮混有 replay 预热，不能拿接近0的训练中位数代表学习成本。RT2 更新次数随新增 transition 数变化（当时中位数1340次），不能把整轮用时变化直接归因加速。

下一轮两 bench 同样应用“先分解计时、同数据验收”的方法：

1. **先定位等待和重复工作。** SAC 拆开前向、反向、优化器、FSDP、同步；环境拆开 reset 的建场景/加载/稳定帧，以及 observation 的渲染/相机回读/变换/RPC。依据 [PyTorch Profiler](https://docs.pytorch.org/tutorials/recipes/recipes/profiler_recipe.html) 和上述 Isaac 性能指南；只在有边界的短测中采样，避免长期 profiler 开销污染正式训练。
2. **复测能省掉的确定性重复计算。** Dojo 先恢复相同布局基线的可重复对照，再把控制状态复用与取消限速拆开；RT2 优先调查 reset 内静态资源是否重复加载。保持种子消耗、帧新鲜度、终止和回放条数一致；不能凭外部组件倍率换后端。
3. **更大的改动往后排。** 场景常驻/reset复用、流水线、全SAC图捕获、专用推理后端都需更完整验收；量化、少去噪步、少UTD和改变batch不属于这轮透明加速。现有 RT2 predict 计时明显小于 reset/SAC，但 CPU 计时可能未完整计入异步 CUDA 工作，应先用 profiler 核实，再决定是否重构推理后端。
