## 1. 先分清四种“并行”和一轮是什么

| 数量 | 当前值 | 实际含义 |
|---|---:|---|
| 在线采集环境数 | 1 | 同时推进一条RoboTwin轨迹；成功或200真实动作结束一回合 |
| 每个观测的候选数 | 8 base + 8 edit | 同一场景提出16种动作方案，Q选1份执行；没有采集16条轨迹 |
| 学习batch | 64 | 从历史replay抽64个窗口做一次梯度更新，不要求刚采到64个回合 |
| GPU数 | 4 | 物理4–7共同分担候选推理和学习计算，不自动产生4个环境 |

每次重规划，π0.5各预测H50动作，取前C10；编辑和Q都处理这10×14维动作。Q从16份候选中选一份执行最多10真实动作，再看新观测。一次episode的成功值只有0或1，所谓“每轮成功率”若指单回合，就是0%或100%；滑动5/10/15/20是最近相应数量回合的平均，分辨率分别为20/10/6.67/5个百分点。它们共享大量回合，不能当成四组独立实验。

一个环境足以定义off-policy学习闭环：数据进入历史池，learner反复随机取batch学习，示范也已在池中。它不要求同时完成一大批轨迹，更不要求“一条轨迹只能训练一次”。单环境的缺点是场景覆盖较慢，连续样本相关、策略在变化，短窗口成功率很吵；滑动平均能显示趋势，不能替代固定种子的额外评估。

实装定位：`train_expo_formal.py:122–135`固定1环境/B64/4卡/8+8；`:395–412`创建单环境并生成8候选。`core.py:539–565`实现候选编辑和Q硬选优。这里的`N=8`是候选数，建议用`N_env`专指环境数，避免混淆。

## 2. 每40动作如何变成学习额度

前10个已完成在线episode仅采集，不产生欠账；之后累计**真实执行动作**，每40个产生1次learner call，回合结束后执行，未满40的余数带到下一回合。提前成功只计实际动作，不按200补齐。

例如warmup结束后：第一回合73动作，做1call，余33；第二回合52动作，与余数合计85，做2calls，余5。总125动作对应3calls、余5。若一回合完整200动作且此前余数为0，产生5calls。这不是“每回合只更新一次”，也不是“每个动作训练20次VLA”。

每个call顺序固定：

1. 20次Q更新；每次新抽B64，并为64个next observation生成8份base候选和8份edit，用选优动作构造TD目标。
2. 1次base FM：从成功demo及成功online的真实H50窗口均匀抽B64，监督更新action expert及投影。
3. 1次editor及1次温度更新，使用最后一个Q minibatch的已执行动作作条件。

所以一个call有20×64=1280个Q样本使用次数、20×64×8=10240份next-base提案；这些是历史窗口重采样与批量模型推理，不能算成新增环境动作。Q使用demo和所有online有效C10窗口；FM使用成功数据。样本单位是物理步起点，窗口可重叠，不是每回合只保留一个样本。

实装定位：`formal_cadence.py:64–102`为额度/余数/完成计数；`formal_replay.py:310–318,445–450,489–520`为窗口与随机采样；`core.py:729–755`为更新顺序。官方 [update L888–938](https://github.com/pd-perry/expo-ft/blob/023cf9cfcb09dab962b6e806fea47d2954b2b9bb/expo_ft/agents/alg/expo_ft.py#L888)同样Q20后base/edit/temp各1；[论文D.2](https://arxiv.org/html/2605.25477v2#A4.SS2)给约40动作一次更新，官方pick示例另设每episode3calls，二者须分开描述。

## 3. 四张GPU实际在做什么

当前使用functional `torch.nn.parallel.data_parallel`：把batch分到模型副本，结果与梯度汇集到可见`cuda:0`，对应物理GPU4；master参数和optimizer留在主卡。它是按数据分计算，不是把一份模型切成四块，也不是把320GB当成一张连续显存。

| 阶段 | 全局计算量 | 四卡分配 |
|---|---|---|
| 在线单观测base推理 | 8份候选 | 每卡2份候选 |
| 一次Q更新的next-base推理 | B64×8 = 512份候选 | 每卡128份 |
| 一次FM更新 | B64 | 每卡16份 |
| Q/editor的观测batch | B64 | 按batch分到四卡，再归并一次全局更新 |

一次call内20次Q更新仍有先后依赖；每次要先构造next候选，再更新Q。四卡不能把20个有依赖的更新当成独立任务同时完成。临时replica、汇集结果和主卡optimizer也有成本，因此四卡并不保证四倍吞吐。

2026-10-03 15:00，在`learner_started`附近的nvidia-smi快照：物理4–7显存分别为**53009/38501/38357/38357 MiB**（约51.8/37.6/37.5/37.5GiB），该次采样GPU利用率均100%。主卡更高与master/optimizer/结果汇集的结构一致；该快照不是峰值证明，也不能代表采集、保存和评估各阶段一直满载。

实装定位：`backend.py:300–332`为主模型与optimizer；`:445–483`候选展平及分卡；`:532–575`FM分卡、梯度归并与一次optimizer step。`core.py:445–470,508–524`为主设备、小组件optimizer及functional DP。显存数字来自本轮独立现场刷新，不由代码推算。

## 4. 熵、α与当前目标为什么有风险

editor是在base建议附近尝试修正。其训练目标可写成最大化`E[Q(s,a+δ)] + α H(δ|s,a)`：Q鼓励有用修正，熵鼓励保留多样性，α调节两者权重。自动温度在平均熵低于目标时增大α、高于目标时减小α；这是[SAC的平均熵约束/温度机制](https://arxiv.org/html/1812.05905#S5)。

这里是连续分布的微分熵，负数正常，而且数值依赖坐标尺度。当前D=C10×14=140，δ=.2z，z经过tanh落在[-1,1]。因此：

```text
H(δ) = H(z) + 140 ln(.2) = H(z) − 225.32
每维 δ ∈ [−.2,.2]，联合熵上限 Hmax = 140 ln(.4) = −128.28
当前目标 Htarget = −140/2 = −70
```

上限来自该140维盒子的均匀分布。要求平均熵达到−70超过上限，因此当前温度目标不可达。实装logprob已计算缩放后的密度，但目标仍沿用未换算的数值；问题不是“熵为负就不正常”。`core.py:64–66`设目标，`:343–350`含scale Jacobian，`:699`为editor loss，`:716`为`α(H−Htarget)`温度loss。

固定官方代码同样默认`adjust_target_entropy=False`，同时在logprob减去`D ln(edit_scale)`。其可选True分支将目标换成`−D/2 + D ln(edit_scale)`，在当前维度/尺度为**−295.32**：这是把缩放前−70换算到缩放后坐标。故风险继承自该官方默认，不是本次PyTorch移植特有；−295.32是坐标一致的对应值，不是已验证的RoboTwin最优参数。[官方目标L286–290](https://github.com/pd-perry/expo-ft/blob/023cf9cfcb09dab962b6e806fea47d2954b2b9bb/expo_ft/agents/alg/expo_ft.py#L286)、[缩放与损失L708–727](https://github.com/pd-perry/expo-ft/blob/023cf9cfcb09dab962b6e806fea47d2954b2b9bb/expo_ft/agents/alg/expo_ft.py#L708)。

13:02快照：223calls，α=1.0698907，相对初始1增加约6.99%；熵估计−129.9551，edit norm=1.39180，editor loss=138.8733。数据符合“温度持续受向上压力”，尚不构成温度爆炸或掉分因果证据。单batch熵只是估计，不能据此断言分布已精确均匀。

α的直接作用范围要说清：它改变editor训练中熵项的权重，进而影响以后生成的修正分布；不直接乘执行动作、不改变±.2边界、不修改FM学习率，也不直接进入候选Q硬选优。当前EXPO的critic TD没有标准SAC的熵奖励项，勿混套公式（`core.py:622–651`）。

editor loss约139还含有密度坐标的常数项；常数本身不产生editor参数梯度。不能把该绝对数值与Q loss直接比较后宣称“熵梯度压倒Q梯度”，需要实际梯度贡献证据。更换目标会改变后续α走势，应作为明确新配方讨论；本轮保留原设置。[SAC作者实现](https://github.com/haarnoja/softlearning/blob/master/softlearning/algorithms/sac.py)亦将策略与温度更新分开。

## 5. 官方同步/异步，与未来4或8环境

论文的原型是真实机器人；固定同步入口只有一个`EnvClientWrapper`和环境step循环。论文支持actor与learner同步或异步，并说明少量GPU时采用同步；实验设备为2×H200。方法没有“只能1环境”的约束。[论文§4.3/§5.1](https://arxiv.org/html/2605.25477v2#S4.SS3)、[官方单环境入口L241](https://github.com/pd-perry/expo-ft/blob/023cf9cfcb09dab962b6e806fea47d2954b2b9bb/train_pi_robo.py#L241)。

官方异步`train_pi_robo_async.py`将GPU0用于采样、其余GPU用于更新（L94–115），仍只创建一个环境（L254）；后台learner持续更新、发布新参数（L313–348）。它是采集与学习重叠，不是多环境采集。该入口replay够一个batch就开学（L498–501），并未按当前10回合warmup及每40动作1call限额运行，因此直接照搬不是零协议变化。[官方README](https://github.com/pd-perry/expo-ft#system-overview)、[固定异步源码](https://github.com/pd-perry/expo-ft/blob/023cf9cfcb09dab962b6e806fea47d2954b2b9bb/train_pi_robo_async.py#L94)。异步网页本轮抓取失败，上述行号由已固定commit的本地官方clone逐行核对。

若后续扩为`N_env=4/8`，仍应按所有环境真实动作之和计数：

| 一批采集，假设各回合都执行200动作且没有warmup/旧余数 | 合计真实动作 | 相同学习额度 |
|---|---:|---:|
| 1环境 | 200 | 5calls |
| 4环境 | 800 | 20calls |
| 8环境 | 1600 | 40calls |

4环境仍只做5calls会将每数据学习量降至1/4；每个环境分别给20k则放大总预算。还需保留总计10回合warmup（明确跨边界的在途回合）、每环境独立seed/RNG/episode/final_obs、同episode C10/H50窗口、每状态8+8候选、全局B64与Q20/FM1的定义。固定评估种子和200动作协议也应保持可比。

当前replay在完整回合后发布；改成多环境整批结束后集中学习，会增加策略刷新间隔和训练突发长度。即使总call数相同，所得训练轨迹也不逐步等价，需要记录策略版本/滞后及回合计数方式。只把`num_envs`从1改4，尚未完成这些语义。

提速应先看瓶颈。若学习和保存占总时间的大头，多开环境只缩短采集部分，固定预算下learner总量不会减少。理想上限可用`1 / (不可并行时间占比 + 采集时间占比/N_env)`估算；实际还有GPU/CPU竞争与同步成本。当前四卡已共同做学习，异步另占采样卡会改变学习资源，需新规模验证，不能把环境数当作加速倍数。

## 6. 评估频率与保存频率的当前边界

当前恢复保存原本已在每回合、每次完整learner call和评估结束后执行，轮转latest/last1；“保存频繁”不等于“保留了很多历史里程碑”。本次授权仅将固定评估间隔25改为10训练回合，保存方式不动；实际生效时间及首次新间隔评估请查看独立receipt。

固定评估是训练期间暂停采集/学习后的额外20回合：4环境×5组、每回合200动作，统计success_once，共4000额外动作，不入replay、不计20k训练预算，并恢复训练随机流。每10回合评一次增加观察密度；保留20评估样本时，成功率分辨率仍为5个百分点。它与在线滑动成功率回答的问题不同：在线曲线描述正在探索的训练行为，固定评估比较同一组场景上的策略能力。
