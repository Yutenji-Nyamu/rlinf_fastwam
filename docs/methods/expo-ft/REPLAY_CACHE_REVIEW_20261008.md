# EXPO 回放缓存：问题、证据、最小修正

2026-10-08；先只读调查，用户随后授权 64 GiB 缓存修正；部署结果见文末。

## 结论

“缓存只留一条”指 **CPU 内存只保留一条已解包轨迹**，不是训练只有一条数据。所有轨迹仍在磁盘、仍参与随机抽样。抽 A → B → A 时，B 把 A 挤出内存，再抽 A 就重复整条加载、构建张量和逐帧哈希；虽然只需要其中若干窗口，仍付出整条处理的代价。

操作系统可能已缓存文件页，因此不能把所有未命中耗时都称为物理磁盘读取。确定的浪费包括重复反序列化、对象/张量构建和完整内容校验。GPU 可能等待 CPU 供数；当前还没有足够分段计时把全部学习时间归因于此。

## 与论文、官方代码的关系

- [EXPO-FT 论文 §3.3](https://arxiv.org/html/2605.25477v1) 规定从经验回放抽样及 actor/learner 更新流程，没有“一条 CPU 轨迹缓存”的算法要求。
- [官方 PiReplayBuffer](https://github.com/pd-perry/expo-ft/blob/21fe3d3b7d913c80836496817965932f49e0aedf/expo_ft/data/replay_buffer.py) 按 capacity 分配 NumPy 内存数组，按索引取图像、状态、动作等。这里没有我们这种单轨迹解包缓存。
- 本地 `rlinf/algorithms/expo_ft/formal_replay.py:220` 写死 `_cache_limit=1`；`_cached` 从394行开始，425行附近执行淘汰。它属于本地磁盘回放接入的实现选择。未找到当初选择1的明确设计理由，不能代替作者解释动机。
- 对照锁定官方当前提交；官方后来的 RealTime EXPO-FT 还含其他缓存，不能与这里的标准 EXPO 回放缓存混为一谈。

## 已有测量

同机 CPU 小测：59帧轨迹39.63MiB，未命中约0.147秒；163帧108.31MiB，约0.495秒。缓存1时再次读取A仍约0.157秒；缓存2时再次命中A约25微秒。该差异仅说明重复读取路径可省，不能直接推算端到端倍数。

当时在线轨迹241条、磁盘22.56GiB，主机可用内存约1.5TiB。文件体积不等于解包后内存，仍应按实际驻留字节设上限。

当前每次学习20次critic更新，每次B64、每个状态8个VLA候选；大量窗口跨轨迹随机抽样，单条缓存容易反复淘汰。这与候选生成/反向传播耗时是三个不同问题。

## 建议的小改动（尚未实施）

1. 保留磁盘作为完整记录，将解包缓存改为**按字节限额的 LRU**；首版可取16–32GiB，达到上限再淘汰，无需占满主机内存。
2. 文件首次进入缓存时完整校验；缓存键包含不可变轨迹身份。若允许文件被替换，命中前核文件身份/大小/mtime，变化则失效并重验。不要每次抽样重算整条哈希。
3. 只加三个累计计时：回放供数、VLA候选生成、critic/FM更新；另记命中率和驻留字节。无需新看护层。
4. 同一抽样索引的张量须逐项一致；保持B64、候选8、UTD20、示范/在线比例及抽样分布。缓存命中不能改变训练方法。

本轮只完成定位与方案，未替换 live replay、未重启训练。

## 获准的最小修正与检查

- CPU 缓存默认上限64 GiB，按需填充；按独立 tensor storage、Arrow buffer及Python对象计费，达到上限才淘汰。缓存不是整个进程RSS的硬上限，单条加载与batch另需临时内存。
- 在线首次加载仍完整核验；命中仅核不可变文件身份，不重复逐帧哈希。示范保持原图像表缓存，命中后被选图片仍解码。
- 缓存内容、命中计数和耗时不进入 checkpoint，不改变 replay RNG、数据池、Q/FM窗口、batch、候选数或更新预算。
- 加三个主机墙钟计时：回放供数、VLA候选生成、其余学习；不加入额外CUDA同步，因此不能当作精确GPU kernel耗时分解。
- 服务器CPU检查5/5通过：命中不重算哈希；相同种子Q/FM数据及恢复状态一致；字节上限/LRU/超大项旁路；已缓存文件被替换时拒绝；tensor别名不重复计费。
- 两条真实轨迹A→B→A，旧版0.144/0.192/0.132秒，修正版0.131/0.146/0.000185秒；三次返回内容摘要均一致。这不是端到端加速倍数。
- 20:03容量核查：246条在线+50条示范；在线tensor storage 22.824 GiB，示范编码图片列约0.782 GiB；至60k动作的基础数据量线性估算约39.69 GiB。主机可用内存约1.56 TiB。

## “20次更新”与论文的计数单位

[论文v1附录C.2及表3/4](https://arxiv.org/html/2605.25477v1#A3.SS2)明确B64、UTD20，并令任务级频率大约为每40个环境步一次学习。论文原实验按任务设置固定每回合1/3/4/6次；本地按实际动作累计额度、回合结束执行，在短成功回合下更精确保持40动作/次，不能宣称逐回合完全一致。

[官方更新代码](https://github.com/pd-perry/expo-ft/blob/21fe3d3b7d913c80836496817965932f49e0aedf/expo_ft/agents/alg/expo_ft.py#L795-L853)将总回放batch分20个minibatch，顺序做Q更新，再做1次base/FM、1次edit和1次temperature。本地20个B64的更新次数与此口径一致，未把基座也更新20次。

| warmup后单位 | Q优化器步 | base/FM步 | editor/temperature步 |
|---|---:|---:|---:|
| 1次学习调用，约40真实动作产生 | 20 | 1 | 各1 |
| 满200动作的回合，5次调用 | 100 | 5 | 各5 |
| 每真实动作均摊 | 0.5 | 0.025 | 各0.025 |

每次调用抽取20×64=1280个Q窗口位置；它们来自整个回放，不代表新增1280条数据，也不保证互不重复。每个Q窗口的下一状态生成8个基座候选，所以每调用有20×64×8=10240条候选生成工作，基座前向成本仍存在。

UTD20旨在多用已有交互数据训练Q，优先样本效率；不是所有任务上已验证的最佳墙钟效率。先修缓存并取得完整调用计时；若仍需减计算，下一项独立对照可考虑Q20→10，保持每40动作的调用频率和base/editor/temperature各1。其代价是每份交互数据获得更少Q训练，效果须实测，不能同时调候选数或把它称为原论文默认。当前未更改UTD，保持20。
