# FQL的Q预热、多任务难度与当前证据

2026-10-27。讨论与只读核对，不修改正式训练、排队FQL或损失参数。

## 有没有前置Q预热

原FQL没有单独的critic-only阶段。论文Algorithm 1在同一个循环更新Q、行为流模型和一步学生；官方代码从第一批直接调用`agent.update`，同时计算Q与actor损失。离线训练后接在线微调的“预训练”，也不是只训练Q。

我们的固定老师版本同样从第一步开始，每轮Q一次、学生一次；两个损失都使用更新前的Q，再分别更新参数及目标Q。Q是随机初始化的四层双网络，老师/学生由预训练π0.5初始化。`train_fql.py:170`的`warmup_steps`仅逐渐升高学生学习率，不会暂停学生，也不会关闭Q对学生的指导。此前多任务为167步学习率预热；这不能称作Q预热。

因此，没有Q预热并非漏抄FQL原算法。但“按原公式启动”不能替代适配后的效果验收。我们的Q已经出现显著高估，需要核对价值学习、动作分布和指导强度，不能说公式正确就排除了实现/适配问题。

## 为什么值得考虑预热，但只等一阵不一定够

Q是评分器，学生会修改动作以获得更高评分。若评分器还没学会区分动作，就立刻让它指挥一个已有能力的学生，可能把学生带偏。先固定策略、让Q学习，再逐渐启用Q指导，是合理候选。

关键是Q多数学习目标也来自自己的预测。例如当前没有奖励、下一状态预测2.2，目标就是0+.99×2.2=2.178。当前预测2.2与目标只差.022，平方误差很小，但两者都超过真实一局最多1分。只多训几百步，可能继续拟合这种偏高目标。

建议候选流程：固定采集策略，先以完整轨迹真实折扣回报检查/初始化Q，逐任务留出轨迹检查校准，再测试启用Q指导后的变化。记录数据动作/学生动作Q、超过1的比例、终点误差与实际成功率。回报均值和成功失败分组只能诊断，不能保证所有动作排序正确；采集策略的回报也不等于另一学生策略的真实Q。切换目标策略后仍需复查。先预热多少步由这些检查决定，不盲搬固定步数。

相关但不同的方法RAPolicy明确使用2560次critic预热，随后每组20次critic、5次actor；它用回放动作与V目标，避免查询学生新动作的Q，actor也不走FQL的dQ/da路线。因此可借鉴“先学评分器”的思路，不能说原FQL要求2560步。

## 多任务是不是更难

有可能。我们的一个共享Q要覆盖46个已采任务、不同场景和决策长度；任务指令在冻结VLM特征里，没有漏掉任务输入。但冻结平均特征能否分辨精细成功条件、不同任务更新是否相互干扰，目前没有实验结论。正奖励只占1759/216842≈0.81%的转移，任务均衡抽样后的训练批约1%–2%，长链与稀疏奖励也会使Q更难学。

原FQL的73项成绩来自分别设置任务的实验，不能当作同一个73任务Q已经验证。多任务本身也不必然更差：MT-Opt用任务条件共享Q联合学习12个真实任务，并在部分任务上利用共享数据获益。因此现阶段应写“多任务是可能困难因素”，而不是“Q高估已证明由多任务造成”。

当前单任务FQL仍排在直接→CP→DMD new→MFD后，尚未开始；仍保持已验收配置，没有悄悄加入预热。它同时更换基座、任务数和C50/200动作协议，决策链最多4块；即使效果改善，也不能仅归因于单任务。
