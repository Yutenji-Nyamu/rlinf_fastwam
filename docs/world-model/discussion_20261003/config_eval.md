# WMRL 并行参数、显存与评估频率讨论 · 2026-10-03

本页只讨论既有只读证据；没有改参数、启动实验或访问SSH。

## 当前并行究竟怎样工作

| 参数 | 当前值 | 具体含义 |
|---|---:|---|
| GPU数D | 4，物理4–7 | 每卡各1个actor/env/rollout角色，共12进程；角色按阶段工作和offload |
| FSDP分片 | `no_shard` | 四卡数据并行，每卡保留模型副本；不是把一个模型切成四份 |
| pipeline stages | 1 | 不做多stage流水线切分 |
| 同时环境N | 64 | 一批全局64条轨迹，每卡Wan batch16 |
| GRPO组大小G | 8 | 同一起点条件的8条轨迹作相对比较；全局每批8组，每卡2组 |
| 顺序采集R | 8 | 依次采8批后再做一次runner轮的训练，不是再增加8倍并发 |
| 轨迹动作预算L | 320 | 固定40个C8 chunk槽位；首次done后的槽位不产生有效actor loss |
| 执行chunk C | 8 | 每次实际执行8动作，Wan预测8帧；直接影响闭环频率和任务行为 |
| 策略预测H | 10 | 每次预测10动作，只用前8个；不等于10步全部执行 |
| 策略/Wan去噪 | 各5步 | 模型内部顺序迭代，不是5个并行worker |
| 全局训练batch B | 2048 chunk槽位 | 每次optimizer step，四rank合计2048；每rank512 |
| 每rank microbatch m | 128 | 一次actor前向/反向的样本数，是训练激活显存的直接控制项 |
| 梯度累积A | 4 | `2048 ÷ 4卡 ÷ 128 = 4`；每4个microbatch才optimizer step |
| update_epoch | 1 | 每轮采集数据训练一遍 |
| 每runner轮 | 512轨迹、20,480 chunk槽位、10次optimizer step | `N×R=512`；`512×320/8=20480`；`20480/2048=10`；都包含最终可能被mask掉的槽位 |

## 哪个参数降显存代价最小

**先保证阶段顺序，再考虑micro128→64。** 已有OOM证据是第140轮actor训练开始后，Wan环境仍占约37.72GiB；阶段等待修复应先确保env和rollout已卸载。单纯缩batch可以留余量，但不能代替消除角色重叠。

`micro_batch_size: 128 → 64`、`global_batch_size: 2048`保持、四卡保持，是合理且对既定方法影响最小的参数候选。代码自动得到`accumulation: 4 → 8`；每轮采样量和10次optimizer更新仍保持。它主要减少actor激活/attention临时张量，不会把模型、优化器或整卡总显存都减半，也不保证Wan生成峰值下降。

已核实际loss路径：虽然配置写`token-mean`，当前传入`loss_mask_sum`与320动作长度时，loss会使用`masked_mean_ratio = (values / (T_i/L) * mask).mean()`。等长名义槽位、同一global batch、64整除每rank512，128→64加倍累积保留同一线性均值目标；不存在“每个micro按自身有效mask数重新归一化”造成的额外权重变化。浮点归约/随机执行仍不保证逐位相同；ratio/clip等日志按micro求均值后再平均，空micro比例变化会影响日志口径。

当前末10轮actor约99秒/1095秒，仅占约9%。即使actor段耗时加倍，整轮也约增加9%，这是代价量级说明，不是实际micro64测速结论。

| 改项 | 主要减少什么 | 代价与建议 |
|---|---|---|
| **m128→64，B2048保持** | actor前反向激活峰值 | 累积4→8；采样量/更新次数保持。优先候选 |
| N64→32，R8保持 | Wan与采样策略的同时batch16→8，部分rollout存储 | 每轮轨迹512→256、更新10→5；1000轮预算的数据和优化量减半，已经改变训练预算 |
| N64→32，R8→16 | Wan/采样同时batch减半 | 保留512轨迹/20,480槽位/10次更新，但顺序采集批翻倍，吞吐和抽样顺序改变；适用于生成阶段确有峰值问题，非本次首选 |
| R8→4，N64保持 | 每轮累计轨迹缓存/主机内存 | Wan同时batch仍16，actor micro仍128；未直接降低这两项激活峰值，且每轮更新减半 |
| G8→4，N/R保持 | 少量组级结构 | 改变GRPO比较组、优势与过滤分布；不是高收益显存项，不优先动 |
| B2048降低但m128保持 | 梯度累积步数 | 单次前反向batch不变，通常不能解决激活OOM，还会增加每轮optimizer次数；不作为首选 |
| C/H/L或去噪步数降低 | 相关序列/模型计算量 | 同时改变控制频率、动作预测和训练任务难度，方法代价明显；不用于这次最小显存修复 |

N要与GPU数、组大小相容；四卡G8时N32恰好每卡一完整组。以上仅作方案比较，不变更当前N64/G8/R8。

## 每10轮保存/评估的收益与成本

当前是`save_interval=40`、`val_check_interval=-1`。**已保存CP40、CP80、CP120**；40/80完成了真实评估，120已通过CPU结构与全浮点参数有限检查，尚未真实评估、也未做完整optimizer恢复。

保存改每10轮能把正常情况下的回退窗口由最多39轮缩到9轮，并定位“推盘子何时明显退化”。但当前每个完整checkpoint很大：CP120六文件实计**16,090,471,299 bytes = 16.09GB = 14.985GiB**，包含约9.144GB的DCP元数据/分片和6.947GB的完整模型权重。

| 保留方式示例 | 完整checkpoint份数 | 仅checkpoint估计空间 |
|---|---:|---:|
| 从0到1000，每40轮全留 | 25 | 402.26GB |
| 从0到1000，每10轮全留 | 100 | 1.609TB（1.463TiB） |
| 从CP120续到1000，每10轮保存，保留现有40/80/120 | 88份新+3份旧=91 | 1.464TB（假设每份同CP120大小） |

不含视频、日志、临时保存空间和其他实验；改每10但全留，比从0每40全留约多1.207TB。现有40/80/120应完整保留；若以后设计滚动保留/里程碑保留，需单独明确清单，此讨论不删文件。

现有**外置原生评估**用额外两卡，20环境×25批=500回合。闭合回执`finished - time`实算（包含阶段启动，不含最终清理）：

| 阶段 | 500回合耗时 | 清理耗时 |
|---|---:|---:|
| 原始模型 | 89.68分钟 | 0.61分钟 |
| CP40 | 86.59分钟 | 1.09分钟 |
| CP80 | 88.43分钟 | 0.61分钟 |

三项连同串行初始化/清理共约4小时27分7秒。训练10轮当前约3小时，因此有独立两卡时，每10轮一次约1.5小时的评估队列在已观察速度下能跟上；仍有约3 GPU小时/次的额外资源成本。若同卡串行，则每10轮约加1.5小时，约为这段训练时长的50%，并非免费监控。当前卡位需另看现场，此页不假定空卡。

**讨论建议：诊断阶段save10合理；评估频率可先每10轮，复用现有独立原生评估队列并按实际资源排队。不要只把训练YAML的`val_check_interval`改10便认为等同已有评估。** 内置eval会复用训练rollout模型/输入设置，且当前env.eval写500并发；现有外置成功协议则是Pi0Eval、双相机C5、20环境分25批及专门渲染/回执。二者不是同一配置或资源行为。长程若保留每10完整评估，需接受时间/资源成本；缩成小样本只能作趋势哨兵，不能替代500回合主成绩。

## 去掉推盘子后有多少提升

仅对**已经完成的同一评估**事后分解：

| 已有模型 | 另外9任务合计 | 成功率 | 相对原模型变化 |
|---|---:|---:|---:|
| 原模型 | 380/450 | 84.44% | — |
| CP40 | 386/450 | 85.78% | +1.33个百分点；相对+1.58% |
| CP80 | 398/450 | 88.44% | +4.00个百分点；相对+4.74% |

这说明全套退化主要由推盘子的48/50→0/50→6/50驱动，能帮助定位原因。**不能用事后剔除的88.44%替代LIBERO Goal全套80.8%，也不能预测“训练时移除推盘任务”后其余任务一定提升4个百分点。** 移除任务会改变采样、奖励、共享参数梯度与总体预算，需要单独命名/比较的实验。

## C8评估要连同相机与推理接口一起说明

当前真实成绩使用原生Pi0Eval、双相机、H10/C5/5去噪；训练使用主相机、腕图mask=false、H10/C8/5去噪与RL采样。只有把C5改C8，并未对齐相机、预处理/归一化、动作语义和推理路径。

旧“head-only/C8”评估已出现**原始模型0/500、CP40 0/500；CP80仅0/350中止**，其全零原因还未解释，不能略过或当作可以直接使用的训练匹配协议。这也意味着目前无法单凭85.6→80.8确定“同训练输入协议下的真实收益”。

更有解释力的讨论路线是：保留现有双相机/C5作原生参考；若另做训练匹配真实评估，先核清旧head-only/C8全零来自输入分布失配、策略输出还是评估适配链。原始SFT在拟用协议的小批基线和轨迹检查通过后，再用同一单相机/C8协议比较原始、40、80、120。需要拆分因素时，可增加同原生接口的双相机/C8对照；不能一次改相机、C、推理器后把差异归因于C。
