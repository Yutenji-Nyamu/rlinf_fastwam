# 代码切口与边界

主线只替换 OpenDW 生成视频的任务判分器；原生RoboTwin保留自己的success标签与最终评估。模型、动作、GRPO和原生控制器沿用旧实现。

1. `qwen_reward.py`复用PR原提示词和单个` True` token概率，冻结bf16权重；不生成文字、不做True/False再归一化。显式视频metadata，记录实际grid和帧数。
2. 离线逐C32块将主相机resize到256×320，去掉重复起始帧及padding，以最近最多16帧评分。沿同一episode顺序读取，每个NPZ只读一次。帧时间基准仍是控制器进度；fps2只是与参考一致的VLM时间编码，不宣称是物理帧率。
3. 服务切口是 `_score_videos`。保留旧ResNet分支。新分支返回块级概率，环境用冻结阈值产生一次二值成功奖励和块末终止，避免连续分数直接进入GRPO。
4. **不直接移植官方局部槽号历史。** N64被拆B16且活跃槽会缩减；采用环境持有每槽历史、请求随行携带历史的方案。reset清空，get_state/set_state保存/恢复，服务本身无跨请求视频历史，避免槽号、重复reset seed与恢复串帧。
5. 评分窗口看到完整块，不能把阳性广播后的首帧误报成“第4动作成功”；奖励和终止归于C32块末，诊断字段也须明确块级判断。

Qwen在独立环境固定transformers4.57.6/tokenizers0.22.1，复用torch2.11，不升级现用π0.5或OpenDW环境。在线接线采用服务直接拥有的独立评分子进程，通过管道传输当前窗口，同步onload/offload；退出时只关闭自己的子进程。WM仍真实B16；Qwen在一个16路请求内串行做16次视频前向，耗时必须按整个请求计算，不能称为Qwen真实B16前向。两卡是否够用须由WM与Qwen共同驻留实测决定，单独VLM显存不能代替这个结论。

处理器实测：8/16帧分别保留8/16帧；奇数11帧按temporal patch补为12帧；原生极短失败块可能只有1帧，显式重复到2帧并登记。模型使用`logits_to_keep=1`和`use_cache=False`，只保留所需下一token logits，分数定义不变。

本轮不加入稠密奖励、多相机判分、U加权、WM更新、改变C32或GRPO预算。若额外变化成为必要条件，先报告具体证据。
