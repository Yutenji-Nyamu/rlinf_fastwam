## 显存为什么炸

已完成139轮；第140轮进入actor训练时，在π0.5前缀Gemma MLP创建`(128,968,16384)` BF16中间张量，申请3.78 GiB失败。日志里的GPU0是worker隔离后的逻辑编号；同卡PID/placement对应**物理GPU6、rank2**。

|故障时同一张卡|GiB|
|---|---:|
|总显存|79.18|
|剩余|3.65|
|actor进程总占用|35.74|
|其中PyTorch已分配张量|23.71|
|其中PyTorch已保留、未分配|9.56|
|EnvGroup rank2，PID2500846|37.72|
|RolloutGroup rank2，PID2500839|2.01|
|本次失败申请|3.78|

37.72 GiB属于本次WM的环境进程；不是把其他用户进程误判成泄漏。actor与环境共驻已经足以解释显存余量不足。缓存碎片仍是次要候选，不能仅凭错误消息中的通用`expandable_segments`建议确定碎片根因。

固定源码路径：runner等待rollout轨迹完成后先启动actor训练，到日志汇总才等待env完成。env发送最后轨迹后还会完成视频flush，再执行Wan offload。当前实配`save_video=true`。所以**轨迹到齐不保证Wan已卸载**，存在阶段重叠窗口；即使前139轮成功，也可能被末轮编码/IO耗时差异触发。CPU回归测试已复现原流程缺屏障，修复副本能保证env完成后才启动actor，且env失败会阻止actor启动。这确认了时序缺陷；实际GPU峰值改善仍需短运行测量。

没有发现当前图像历史无限增长：源码裁剪保留窗口，世界模型推理在no_grad范围。梯度/actor耗时也未出现持续爆炸。这些只排除部分候选，不能代替内存曲线证明没有泄漏。

## 以前有没有显存、内存曲线

**本次训练没有连续的VRAM/RSS/PSS时间序列，也没有torch allocated/reserved的阶段记录。** 39个标量均为训练/环境/时长指标；已有managed-identities用于进程身份和精确清理。过去人工快照与这次OOM快照不能拼成完整训练内存趋势。故当前答案是：有故障瞬间显存数据，无法判断是否随轮次单调上涨。当前服务器可用主存充足，也不能反推故障前主存曲线。

区分三类量：张量allocated、分配器reserved、整进程nvidia-smi显存。reserved会包含可缓存的空闲块，不能全部叫泄漏；应按同rank、同训练阶段的最低水位和峰值比较。[PyTorch显存说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html#memory-management)

## 真实效果：哪里下降，哪里改善

各检查点均为相同官方native部署合同：双图、H10/C5、M5、320动作、500个唯一初态、每任务50回合。

|指标|原始|CP40|CP80|
|---|---:|---:|---:|
|全套曾成功|428/500，85.6%|386/500，77.2%|404/500，80.8%|
|全套末尾成功|76.8%|57.2%|69.2%|
|推盘子到炉前|48/50|0/50|6/50|
|其余9任务合计|380/450|386/450|398/450|

CP40总计少42次成功，推盘子单独少48次；CP80总计少24次，推盘子少42次，其他9任务净增18次。这是**明显的局部能力退化**，不是十个任务一致下降。末尾成功率也下降，说明按另一种更严格统计口径仍没有整体收益。真实模型种子/一次固定评估不等于多训练种子稳定结论。

CP120目录、DCP元数据/存储范围、完整模型所有浮点参数有限性已在服务器CPU核验；未实际恢复optimizer，未做CP120真实环境评估。因此不能给第139轮模型编造最终成绩，也不能从40/80两点外推趋势。

## 训练究竟学了什么

|首10轮 → 末10轮|观察|
|---|---|
|WM代理曾成功率 0.859% → 4.824%|有上涨，不能当真实LIBERO成功率|
|有效loss动作块占比 2.823% → 6.509%|末10约93.49%槽位无policy loss，含done后mask与整组过滤，不能称93.49%组被过滤|
|136轮正mask，3轮全mask=0|真实第4/5/6轮仍会执行AdamW更新；不等于完全没改权重|
|末10梯度范数均值1.710；全程最大2.764|训练loss/grad有限；LR固定5e-6，未发现数值爆炸|
|末10approx KL≈0.00915；clip≈5.29%|不能证明reward正确，但未见明显策略更新数值失控|
|末10actor约99秒；采集约991秒|约90.5%轮耗时用于生成数据，有效mask少也照常计算名义batch|

`env/return`是固定320动作结束时的环境统计，而actor训练用首done截断的轨迹，两者结束时刻不同。环境return近零与success_once上涨不能单独证明reward hacking。另有有效mask上的`rollout/rewards`均值上涨，但不是轨迹成功率。现有全局标量缺少每任务有效组数、逐帧reward翻转、KIR起点判分，尚不能定位推盘子受到哪些错误梯度。

## 实现、配置、数据与论文的交叉判断

1. **训练与部署的输入/闭环不同，已确认；因果占比待隔离。** 当前训练屏蔽腕图、C8，评估双图、C5。π0.5仍是预训练H10，C8取前8个动作并不等于已适配该闭环。原始与CP40/80按同部署协议比，退化结果成立；但不能只凭结果把原因唯一归给相机或WM。
2. **当前不是官方原样Wan+π0.5配方。** 固定Wan例程是OFT；本轮继承π0.5的优化配置，再接单相机Wan。维护者曾明确指出接口及chunk缺口。观察mask接口可运行，不等于屏蔽预训练输入无代价。[维护者说明](https://github.com/RLinf/RLinf/issues/831#issuecomment-4102834159)
3. **策略与冻结WM的行为分布可能不匹配。** RLinf冻结OFT例程Goal为48.2%→60.1%；WoVR论文48.2%→77.5%还包含改进策略采样后再次对齐WM。本轮Wan/奖励固定，没有PACE更新，且起点换成85.6%的π0.5，不能套用论文增益。[RLinf例程](https://rlinf.readthedocs.io/en/latest/rst_source/examples/embodied/wan.html)、[WoVR](https://arxiv.org/html/2602.13977v1)
4. **奖励语义值得优先检查。** 逐帧分类→差分奖励；chunk内短暂成功、末帧回失败可以记success却净奖励0。KIR重置时前一奖励设0，没有先评分其起点。本轮另以原奖励模型/原预处理/原阈值在CPU评完742个实际reset画面：496初始＋246 KIR末帧均为stored0、pred0；推盘79个也全部为0。这排除了“该reset集合已经被RM判成功、reset归零直接白拿分”的具体候选；不包含成功正例与生成画面，不能证明RM召回率或生成域精度。逐帧翻转/信用分配仍需轨迹证据，不能直接断言reward hacking。
5. **有效数据少而无补采，已确认。** 当前整组过滤只置零mask；不会像WMPO补足固定有效batch。GRPO会放大少数组内相对差异，错误奖励也可能因此获得较大权重。当前无显式SFT参考KL/BC锚定，可出现任务遗忘；这属于候选机制，并非凭此就修改算法。[WMPO](https://arxiv.org/html/2511.09515v1)
6. **初始化数据不是均匀的10任务/两类起点。** 742文件=496初始＋246 KIR；按文件均匀抽样，各任务51–97文件。推盘子49初始＋30 KIR，共79/742≈10.65%，排除“完全缺少此任务数据”。这只是reset集合，不是Wan预训练1500条rollout的完整训练集；不能混称。
7. **已排除若干容易误判的问题。** 固定源码实际有按轨迹长度归一化；reset上游修复已包含；reward内部推盘ID2与评估task_id5是不同合法索引；此π0.5配置不条件化state，零state占位不能直接判定缺本体状态为根因。现场训练核心源码与固定上游一致，已有两文件适配仅涉及输入接口。

## 本轮已落实与下一步

已准备独立、可审阅的阶段屏障补丁及轻量监控；**没有修改原r6运行源码、没有重启WM、没有打断新RLT或共享Ray**。

- 进程边界监控：env卸载前后、rollout加载/卸载、actor加载前后/训练结束，记录allocated/reserved/峰值/碎片统计，按PID分文件；只有显式启用时工作，不初始化CUDA或强制同步。
- 服务器CPU验证：原流程重现缺屏障；修复流程阶段顺序正确；env异常时actor不启动；监控helper不初始化CUDA。外部监控在SZ3实际只读采样成功。
- 未做GPU诊断，尚不能宣称OOM已修复。待诊断的最小改动是同步与日志；先保持N64/G8/R8、micro128/global2048、LR、C8、KIR等方法/预算原状，不先用缩batch掩盖问题。

建议顺序：①在新的独立借还scope安排CP120恢复与少量完整轮次，核对同阶段最低显存和峰值，任一OOM/非有限/归还异常则结束诊断并按唯一owner归还；②用已有CP120补同部署口径评估，并优先检查推盘子真实轨迹与RM标签；③明确相机/C差异的代价，再决定是否继续1000轮或做方法改动。短诊断的具体轮数、资源占用和新实验预算需在实施方案中明列；本轮尚未启动这些实验。
