# OpenDW 并行与资源利用率讨论 · 2026-10-04

本轮按用户要求只读分析，未暂停或改变正式训练。依据 15:48 资源快照与 15:51 首轮时间窗口核验：资源利用率确实偏低，优先处理同步开销和真正的 WM 并发；单独把 N64/R8 换成 N128/R4，不能解决当前 B1 排队瓶颈。以下为讨论方案，尚未实施。

## 当前究竟并行多少

| 参数 | 当前值与含义 |
|---|---|
| 环境 N / 组 G / 采样 R | N64/G8/R8；一次管理 64 条轨迹，分 8 批收集，每轮 512 条；G 已包含在 N 中 |
| 每条时间长度 | 上限 384 动作，每块执行 C32；最多 12 块按时间依赖串行，策略仍预测 H50 |
| 策略 | GPU4/5 各一个 rollout rank，同时承载两个 actor rank；actor global2048/micro8/U2 |
| WM | GPU6/7 各一个服务，每服务管理 32 个逻辑环境；HTTP 可携带多条，内部逐条 B1 推理 |
| 真正 WM 同时生成 | 两服务各一条，合计最多 2 条视频；N64 不等于 WM GPU batch64 |

理论上限为每轮 512×12＝6144 个视频块；提前成功后不再调用 WM。首轮实际生成 GPU6 990 块、GPU7 1003 块，共 **1993 块**，与 `124.5625×512/32` 一致。服务请求只覆盖仍活动的环境；`call42` 这类请求序号不表示单条轨迹执行了 42 块，也不构成 C32 接口冲突。

正式首轮已出现有限、非零梯度，区别于短 smoke 全滤、零梯度；这证明计算更新发生，**不证明原生任务改善**。99.2% 是 WorldArena 奖励模型对生成图的代理判断，仍须看轨迹与原生 RoboTwin 评估，不能报告成真实成功率。

首轮采样窗口内，WM6/7 心跳采样的 GPU util 均值为 **10.05% / 10.43%**（317/326 个样本）。15:48 额外 16 次快照覆盖约 19 秒：GPU4/5 均 0%；GPU6 均 12.69%、范围 0～33%；GPU7 均 12.12%、范围 0～31%。该短窗口的显存固定为 17293/17585/27798/27798 MiB，策略卡此时在等环境。短窗口不能代表全轮；显存用量也不等于计算利用率。

另一个统计口径是截至 15:48 的整个 formal 阶段：WM6/7 全部心跳 util 均值 8.01%/8.76%，含装卸、训练等待及第二轮部分采样；筛选 WM/RM 推理标签后为 10.57%/11.45%。标签仍会覆盖推理后的保存和监控，不能称“纯 CUDA kernel 利用率”。不同窗口不混用。

## 时间花在哪里

首轮服务请求的配对墙钟与逐条计时如下，两服务并行，不能把两列相加当整轮耗时。

| 首轮采样窗口 | WM6 | WM7 |
|---|---:|---:|
| 完整请求数 | 48 | 50 |
| 请求墙钟总和 | 4005.89 秒 | 4141.00 秒 |
| row 计时总和 | 2278.84 秒 | 2352.74 秒 |
| 墙钟减 row | 1727.06 秒，43.1% | 1788.26 秒，43.2% |

row 计时在同步 `_save_sample()` 之前截止，也不含后置 `row_completed` 资源日志；前置 `row_started` 日志却在计时内。因此 row 也不是纯 GPU 计算时间。差额主要待分解为同步媒体保存、逐条资源日志和其他请求处理，不能把全部约 43% 归到某一个来源。

资源日志确有可测成本：一次只读 `nvidia-smi` 子进程调用，4 次实测为 0.17～0.21 秒；每个 row_started/row_completed 各有两次调用。两条日志合计四次子进程启动，可能对约 2.3 秒的单条流程产生明显影响，但其部分已含在 row 计时内，不能再把它与差额直接相加。

两个服务已经各存满 640 个样本目录，此后自动不再保存新媒体。因此后续轮次可能自然变快；尚不能把首轮保存开销外推为每轮固定开销，也不能把未来提速全部算作其他修改的收益。

## 推荐讨论顺序

1. **先减少同步开销，保留简要监控。** 将逐条外部命令采样改成低频后台采样；关键装卸/异常保留即时记录。只保留少量有代表性的媒体，考虑有界异步保存，避免采样线程等待编码写盘。现有前 640 个样本保留用于诊断。先对比保存额度耗尽后的自然稳态，再归因优化效果。
2. **继续 N64/R8，单独提高真实 WM 并发。** 两个可选实现如下，先不同时改 N、R 和 actor micro，保持每轮 512 条与学习预算便于比较。

| 方案 | 获得什么 | 适配与限制 |
|---|---|---|
| 每服务真 B2，共享模型权重 | 两卡合计每次生成 4 条；可能更有效利用GPU | 官方入口偏单样本；需适配图像/动作批量、缓存、每样本 seed 和输出拆分，显存与数值合同待测 |
| 每卡两个独立 B1 服务 | 总共 4 个并发预测，复用已跑通的单样本路径 | 粗算每卡约 54 GiB，仅为两份当前常驻量的估计；实际峰值、争抢与吞吐须测。路由和 owner 要管理 4 个独立服务 |

3. WM 吞吐上来后，再比较 **N64/R8 与 N128/R4**：两者都是 512 条轨迹。单独换 N128/R4，双 B1 的总预测工作仍相同，可能减少部分同步开销，但也增加排队、策略推理批量和缓存，不应作为主要提速手段。
4. 利用 GPU4/5 也放 WM，分摊到四卡，可作为后选；它需要与策略共卡、安排训练前卸载并验证峰值，改动更大，当前先不扩。
