# 队列写满处理与RLT候补 · 2026-10-30

## 现场与行为

本轮仅改等待中的400轮/FQL-fix队列和空等中的RLT CPU调度器；正在运行的多任务Direct、单任务v2训练没有重启。当前v2继续按既有latest2+best保留策略运行。

原队列按方法捕获错误后继续下一项，但失败处理会先写同盘JSON/日志。若Home/Data已满，写失败回执自身也报ENOSPC，原逻辑可能在清场/接下一方法前退出。现增加：

1. 每段训练前，以方法实测完整保存点大小加余量做空间预检：Direct8、CPv2 10、DMD/MFD14、FQL8 GiB。
2. ENOSPC/EDQUOT导致主目录不能记录失败时，写本用户根盘`/tmp/chenyiteng-queue-*`的简短回执；清理本阶段自己的进程后继续下一方法。其他类型写错误不静默吞掉。
3. 不自动删历史权重、不把半个保存点当成完整点。全部后续方法若都没空间，可能连续跳过；这时接RLT仍需其保存盘可写。

测试模拟了保存失败和事件日志失败，确认清场先于下一方法启动；连同原队列预算/保留测试13项通过。没有通过真的写满服务器来试验。

## RLT登记

发现已运行owner只在启动时读plan，因此仅修改plan不能保证活进程采用新登记。修复后每轮刷新plan，并检查UID、boot ID、卡集合不变。精确重载仅等待中的CPU owner，保持所有训练owner不变。

根盘预置交接许可（明确标记armed，不是假冒训练完成回执），仍需对应队列owner退出、当前v2前驱退出、GPU无进程才能接RLT。额外前驱条件避免后续队列异常退出时，在健康v2评估切换间隙抢卡。
